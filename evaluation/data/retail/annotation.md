# 中文数据标注与评测约定 v1

本版采用主意图识别＋辅助诉求记录。没有前置子查询拆分、依赖图、执行任务表或多标签识别指标。所有样本由本轮助手自编并复核，属于小规模合成开发资料，未经独立人工标注或真实用户验证。

## 1. 主意图

每条当前用户消息只有一个 `primary_intent`，使用现有 IntentCategory 中的值，不为本次数据另加枚举。不能因为语气急、抱怨或出现“退款”一词，就覆盖用户实际要做的事。

| 值 | 含义 | 正例 | 边界 |
| --- | --- | --- | --- |
| order_status | 查询本人订单、订单商品／金额和已记录的配送信息 | 查这单有没有送达 | 问一般可退状态属于 query；全店最低价属于 other |
| refund | 明确要求办理、继续或改变退货申请 | 帮我申请退这件商品 | 仅询问政策、明确先不要办不是 refund；是否符合条件另由工具判断 |
| query | 范围内的政策、准备或流程咨询 | 礼品卡能接收退款吗 | 不能把具体订单事实只当知识问答；此类内部用 scenario 区分政策／准备，不新增主标签 |
| human_handoff | 明确要求真人接手、停止自动办理并交接 | 不要继续操作，转人工 | 抱怨或不满本身不等于要人工 |
| greeting | 无业务目标的招呼、感谢、结束与礼貌回应 | 谢谢解释，再见 | 含实际办理目标时按业务目标分类；有确认上下文时不能把 yes 一律当寒暄 |
| other | 目标不足、明确撤回且无新目标，或本轮不支持的业务 | 帮我改地址／这个怎么办 | 不自动扩展到取消、换货、发票、推荐等服务 |

复合请求先读完整当前消息与给出的 history，尊重否定与当前改口。明确交接优先；否则显式办理退货优先于附带查询和说明；明确查本人记录优先于附带知识咨询。只有知识问题则 query，只有礼貌回应则 greeting，没有可确定支持目标则 other。该优先级用于唯一主标签，不授权越过确认。

`auxiliary_needs` 记录额外的 order_query、return_application、policy_explanation、return_preparation、human_handoff、unsupported_operation。没有则空列表。它不作为本轮识别器必须预测的第二输出，也不计入 Accuracy／Macro-F1；后续检查业务是否完整时再使用。不能把“不要退”的目标记成待执行辅助诉求。

120 条为 6 类各 20 条、30 个场景家族，每家族 4 条。dev 72、test 48，两侧各包含全部 6 类。历史只保留用户可见内容，不把工具尚未返回的事实塞进去；当前识别 API 支持 history，但现有 IntentEvaluator 尚未透传，第三步需局部适配后才能计入这批上下文样本。

## 2. 槽位

每个槽位记录 type、text、start、end，偏移是 Python 字符索引，左闭右开，当前 message[start:end] 必须恰好等于 text。仅标当前消息显式内容；history 用于理解意图，不要求本轮实体抽取从历史或数据库补值。

| 类型 | 标注内容 | 不做什么 |
| --- | --- | --- |
| order_id | 显式订单号，如 #W9000101 | 不根据商品猜订单，不给只有数字的错误单号臆补 W |
| item_id | 用户明确说商品编号／item_id 的具体款式号 | 不把 product_id 或任意十位数字冒作 item_id |
| product | 实际出现的商品词，如耳机、平板、T恤 | 不从“那件”补商品，不把电子书改写为平板 |
| payment_method_id | 显式礼品卡／PayPal／信用卡标识 | “原路”“另一张卡”不臆造具体 ID；它们应由后续业务澄清或查询 |
| quantity | 明示的“一台”“两件”“一双”等表面片段 | 不推断未说出的数量，不把第一个的序数当件数 |
| amount | 显式货币片段，如120元 | 不把订单号数字当金额，不把用户估计当已核实支付事实 |

表面抽取的类型＋文本集合为基础评分单位：先按本文件固定规则规范化，再按整套样本汇总 TP／FP／FN 得到微平均 Precision／Recall／F1，并报告每槽位支持数；样本 Exact Match 要求该样本全部槽位集合相同。零槽位样本也要计入 Exact Match，以发现误抽取。

唯一允许的标识展示规范化：去首尾空白；已有 W 与数字的订单号可以统一前置 #，不更改数字，不把纯数字推测为订单。商品／数量／金额仅去首尾空白，不使用同义词、货币换算或答案驱动的替换。

同值多次出现可保留多个跨度，评分集合去重。这个指标不能证明商品与数量的配对正确，也不能证明待退列表完整；第五步的业务夹具另检查。当前金额、item_id、支付标识的测试支持数很少，只能作初始回归，不能据单个样本宣称该槽位准确率可靠。

识别器目前仅抽取 order_id、product（空）、date、amount、error_code；本版并非其已有能力的成绩单。第三步应保留原始输出并按预先约定评分，缺少的槽位记 FN，不在评测适配器中偷偷从 message 重抽补齐。date／error_code 不属于本版目标槽位，不纳入这些槽位分数。

## 3. 标签映射与意图指标

labels.json 冻结主标签、辅助值、目标槽位和当前原枚举值。仅将 logistics → order_status、escalation → human_handoff 视作同义类别合并；原枚举中其他范围外类别合并到 other。保留模型原始标签，不能看期望答案再改映射。无法解析、调用失败、未知标签单列错误，不用 other 伪装成有效解析。

Accuracy = 主意图正确数／全部计划样本数。Macro-F1 固定对这 6 类求各类 F1 的平均，分母为零的类 F1 记 0；预测未知或失败仍令真实类产生 FN。失败不能从样本分母静默删除。历史、Prompt、模型、配置与费用记录属于第三步，第二步不生成模型性能数字。

## 4. 检索相关性

knowledge.jsonl 的 29 个稳定 evidence_id 是检索与引用单位，归属 9 个主题；不是运行时任意 chunk 的位置。输入 retrieval.jsonl 包括 48 问：dev／test 各 24，其中各 20 个 answerable、2 个 needs_tool、2 个 unanswerable。

- qrels 的 2 表示直接支持完整答案，或多问题中的必要组成部分；1 表示主题相关但缺少所需结论／限定；未列入为 0。不得因关键词相同就标 2。
- required_evidence_groups 表示需要覆盖的证据组。同组多个 ID 是等价替代，命中任一即可；不同组需要全部覆盖。例如同时问改口确认与能否换卡，需要两个独立依据。
- answerable 问题才进入 Recall／MRR／Hit 分母。以 qrels≥2 为相关，去重后按原排序在 k=1／3／5 检查：Recall@k 为召回相关段占所有相关段比例；MRR@k 为首个相关段倒数排名，没命中为 0；Hit@k 为至少一个相关段命中。
- 对多证据问题另报 AllEvidenceHit@k，即每个必要组至少一个命中，避免只答一半也显得成功。标准 Recall 仍按段计算，不能把证据组覆盖率冒充标准 Recall。
- needs_tool 是必须查询当前订单的事实，知识库没有该值；unanswerable 是语料没有具体答案。两者不伪造 gold 文档、不以“没检索到”直接判系统正确，另检查是否正确转业务查询或说明无法确认。
- 对 unknown 时间、包装等问题，若已有明确“未规定”的证据可以回答边界，则可作为 answerable；没有支持具体答案的资料时应保持无答案。不能为了每问都有正例强标相关。

相关性由本次助手逐组核对，并未经过双人独立标注或大规模用户验证；标注是可审阅的 v1。模型回答质量、引用是否支持、忠实性与完整性尚未运行。旧演示文档不在固定语料内，不作为相关性 gold，也不应在第三步混入同一集合。

## 5. 划分与来源

splits.json 明确列出家族，相关样本同侧；所有编号、用户话术与目标均为项目自编，source_task_ids 为空，不是 τ³-bench 任务译文。不使用上游隐藏用户计划、gold、真实用户数据；订单标识只是语法测试占位，不代表已初始化的业务库。

这套资料是助手已阅读的固定合成比较集，不称独立盲测，不代表真实流量分布。对同一数据的优化必须保留 dev／test 原划分与版本；不能把测试错误改标签来制造提升。语料内容是共同可检索知识，两侧共享语料属正常设置；近似查询家族不得跨侧。

第三步先在固定语料与数据上跑现有方法，第四步只根据主要错误优化并报告成本／延迟。小知识库还应与完整政策上下文等简单方案对照。这里不预设检索改写、重排或未来子查询拆分一定有益。
