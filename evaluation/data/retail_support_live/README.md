# 支持场景真实小样本对话脚本

本目录保存 T18 的固定脚本用户、有限分支和判定口径，并被 T19 退货路由复验复用。它不是用户模拟器平台，也不是新的业务资料；运行器直接调用生产 `RetailService`，脚本用户只根据真实可见回复、已展示待确认详情和 Host 事件推进。

当前脚本为 `t18.4`：统一生产状态与脚本对当前退款去向询问的识别，覆盖列表、二选一及带人称指代的选择问法；分句区分当前询问与后续步骤。未知退货回复立即记评测错误并停止后续付费案例，明确业务拒绝仍是业务结果。用户消息、确认门槛与原场景目标不变。历史 `t18.1`—`t18.3` 的结果、费用和无效判定完整保留。

## 文件

- `cases.json`：S01—S04 的完整用户原文、有限澄清、重启点、确认门槛和预期业务状态。
- 运行器：`evaluation/run_retail_support_live.py`。
- 定向测试：`tests/test_retail_support_live.py`。

## 固定顺序

`S01A、S01B、S02B、S02A、S03A、S03B、S04B、S04A`，每组每案一次，共 8 条正式对话。S01 这一对同时作为真实烟测，进入主表并计费。不因首条结果替换后续任务或调整顺序。

## 脚本边界

- 只在真实回复包含可用且未重复的建议后推进到“已解决”或“人工”反馈。
- 退货确认只在完整、正确的待确认详情已于前一个独立用户轮展示后发送；准备与展示同轮、错误目标、未展示详情都不确认。
- 身份与目标最多各补充一次；达到用户轮上限即停止并记业务失败，不为失败模型补试。
- S03 在第一次出现未重复建议后关闭并重建 runtime／MCP，使用同一 SQLite、会话、事件日志和唯一账本；重启本身不产生业务写入。
- S01／S04 不提供退货授权；S01 无订单写入，S04 只有模拟人工交接事件。
- S01 发送解决反馈、S04 发送人工请求并接收回复后即结束；是否实际解决或成功交接由结果断言判断，不再发新一轮排查。
- S02／S03 仅在模型明确询问退款去向时回答一次“退回原支付方式”，这只是去向选择。仍须完整详情展示后的独立确认才允许提交；重复询问不会无限补答。
- S03 尚未选择退货时只补充排查信息，不提前进入身份／退款分支。
- 汇总保留 `execution_valid` 的正常结束含义，另以 `evaluation_valid` 计算有效分母；已有 `validity.json` 中 `script_valid=false` 的案例不会计入配对。

## 命令

运行器提供 `preflight`、`live`、`summarize`，均要求 `--run-id`。`--plan` 选择冻结计划：默认 `t18` 保持八条历史口径；T19 退货路由复验显式使用 `t19`，固定顺序 `S02B、S02A、S03A、S03B`，共 4 条计划对话、2 个计划配对，汇总不把未计划的 S01／S04 算作缺失。每次运行必须使用新的独立证据目录，不能覆盖历史结果。

独立复验另加 `--ledger-run-id`，把新证据目录与原 T18 唯一账本分开：`preflight` 只读取原账本副本计量，`live` 才追加原账本；原账本 `run_id`、预算、价格、模型必须一致，不会因新 `run-id` 重置额度。`preflight` 不调用收费模型；`live` 必须显式执行，使用累计 5 元的预算约束；`summarize` 会重新写入所选目录的汇总文件。

`--plan t19-final` 用于同一版本的最终基线验收，顺序为 `S02B、S02A、S03A、S03B、S01B、S04B`：multi四场景、single两条退货兼容对照，共6条，只有S02／S03的2对参与配对比较；未计划的S01A／S04A不算缺失。预算计划只计算这6条，逐组预留与原5元账本硬上限不变。必须独立冻结并取得实际调用授权，不自动运行。

首次证据目录 `t18-support-20261020` 只作历史记录，不得对其运行 `preflight`、`live` 或 `summarize`。T19 复验示例：`--plan t19 --run-id t19-support-20261020 --ledger-run-id t18-support-20261020`；该示例只说明参数，不表示已授权或已执行。复验仍须保持固定顺序、固定脚本和原 5 元累计口径，不能覆盖首次结果。T17 旧场景与资料保持原样。
